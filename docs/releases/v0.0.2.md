UniDrive CLI v0.0.2

JVM artefact for the coordinated UniDrive release (the signed jar and its SHA-256). Distro packages and the end-user tarball are produced by
unidrive-dist and published at https://unidrive.krost.org/install/.

Verify with:

    gpg --verify unidrive-0.0.2.jar.asc unidrive-0.0.2.jar
    sha256sum -c unidrive-0.0.2.jar.sha256

Everything since v0.0.1 is in the compare view: https://github.com/gkrost/unidrive/compare/v0.0.1...v0.0.2 (about 270 changes). The notes below
are the parts a user or a packager notices.

## New

- **Providers:** Dropbox and S3 over the provider SPI. Dropbox signs in across processes with a pasted code (`auth begin` / `auth complete`) and resumes an
  interrupted upload session at the committed offset.
- **Read-only views:** a framework for showing what an account holds apart from the drive: the Shared view (what the account shares, Internxt) and the provider's
  trash in a read-only folder, on by default where the provider has one, listed, read and refused on the wire.
- **Ignore rules:** a git-conformant ignore matcher; rule files are discovered, layered and cached per sync root (also a rule file only the cloud holds); the
  mirror's scan and plan apply them; a mount holds ignored paths back from upload and says why.
- **Daemon:** pause and resume (also timed, `until_ms`); upload, cache, provider and credential health and an upload attempt limit with the next try in
  `daemon.status`; `history.list` / `history.subscribe` over the transfer history; per-minute request roll-ups; a machine-readable `last_error_code`;
  write-handle ids issued by the daemon; a fail-fast on credentials that need an interactive sign-in.
- **CLI:** the account lifecycle (`profile list --json`, `profile set`, `profile default`, non-interactive `profile add`, `profile remove` that refuses a running
  or busy profile, `auth begin|complete|login`, `logout --json`), `scope show|set|clear` for the standing sync scope, `pending list|drop` to recover stranded
  upload rows, a periodic daemon health line.
- **State:** `state.db` in WAL mode with `synchronous=FULL`, a faster writer path, an in-memory row count, the staged scan in a file of its own, and merges
  in bounded chunks: far shorter holds of the state monitor on large drives.
- **Internxt:** resumable folder walks, folder paths resolved from the rows the listing saw, shard hash verification (RIPEMD-160 of SHA-256), permanent
  download failures told apart.
- **Duplicates:** remote items with the same name are kept under decorated names and listed in status.

## Fixed (selected)

Data safety and correctness:

- A remote rename onto an existing local file keeps that file as a conflict copy; a conflict whose download fails leaves no empty stub; keep-both copies never
  overwrite an earlier copy; a new file is never taken for a sparse stub by its content.
- A hydrated file whose new cloud content has not been downloaded yet is no longer treated as in sync; a remote rename that comes with an edit fetches the
  edit.
- `StateDatabase.batch` rolls back on an `Error` instead of committing half; the delta merge finds a row by its remote id first, so swapped and chained
  renames keep each row's baseline; an item that changes kind (file/folder) starts a row of its own.
- A mount no longer writes back a row for a cold read that finished after the file was deleted or renamed; an unsynced edit is remembered with the version it
  started from and replayed against it.
- `conflicts restore` writes under the sync root; a move in localfs never overwrites, a copy goes through a staging file; a file the hash compare cannot read
  no longer aborts the local scan.
- QuickXorHash follows Microsoft's algorithm (the earlier one produced other values and overflowed at about 186 MiB).

Security:

- Sign-out revokes the token where the provider has a revoke call (Dropbox) and no longer claims `revoked: true` otherwise; the vault is replaced atomically
  through an owner-only temp file; pre-authenticated URLs in exception text no longer reach logs, the audit log or IPC; the OAuth loopback wait, IPC UTF-8
  lines, the pid file, owner-only temp copies and pending sign-in files were hardened; pending device-flow credentials are cleaned on logout.

Providers:

- Internxt: a failing proactive token refresh keeps a still valid token in use; a file is found by its full name only (no base-name fallback); a download is no
  longer cut at 600 s in total; resumed scans keep the modification time; hex decoding accepts ASCII digits only.
- OneDrive keeps the stored refresh token when a refresh omits it, follows `sharedWithMe` paging; S3 treats a 403 for one object as that, not as a failed sign-in;
  S3 and Dropbox uploads are no longer cut by the 60 s socket timeout.

## Behaviour changes to know

- Several CLI failure paths now exit non-zero (`trash restore`, `versions restore`, `free`, `get` after skipped downloads, `sync --watch` stopped by an
  authentication error), and `free` refuses a file that was never uploaded.
- Configuration values the schema refuses are refused by key name with exit 78 (`poll_interval` below 5, an unknown `sync_direction`, a negative
  `hydration_cache_max_bytes`) instead of failing later or being read leniently.
- `trash purge` and `versions purge` use the profile's configured retention (`trash_retention_days`, `version_retention_days`) instead of fixed 30 and 90 days,
  and print the value and its source.
- `profile add` for a backup profile writes a mirror profile the parser reads, with its upload policy in a section of its own.
- Windows device names (`CON`, `NUL`, `COM0` ...) are refused by one shared rule for engine, profile and folder names.

## Compatibility

The IPC protocol version stays 2; the additions to `daemon.status`, `history.*` and the corpus are additive. Under the 0.x rule of the distribution design
(0.MINOR for a breaking CLI or IPC change) the exit-code and validation changes above are the ones to weigh; they are the only places an existing script could
notice a difference.
