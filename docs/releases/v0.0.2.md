UniDrive CLI v0.0.2

JVM artefact for the coordinated UniDrive release (the signed jar and its SHA-256). Distro packages and the end-user tarball are produced by
the distribution repository and published at https://unidrive.krost.org/install/.

Verify with:

    gpg --verify unidrive-0.0.2.jar.asc unidrive-0.0.2.jar
    sha256sum -c unidrive-0.0.2.jar.sha256

Everything since v0.0.1 is about 475 changes: about 270 when these notes were first written (2026-10-24, the day the engine moved to this repository) and
205 merged pull requests after that, up to 2026-11-04 (commit 42eb2732). v0.0.1 predates this repository's published history. The notes below are the parts a
user or a packager notices; the section "Since the first draft" holds what came after 2026-10-24.

## New

- **Providers:** Dropbox and S3 over the provider SPI. Dropbox signs in across processes with a pasted code (`auth begin` / `auth complete`) and resumes an
  interrupted upload session at the committed offset.
- **Read-only views:** a framework for showing what an account holds apart from the drive: the Shared view (what the account shares, Internxt) and the provider's
  trash in a read-only folder, on by default where the provider has one, listed, read and refused on the wire.
- **Ignore rules:** a git-conformant ignore matcher; rule files are discovered, layered and cached per sync root (also a rule file only the cloud holds); the
  mirror's scan and plan apply them; a mount holds ignored paths back from upload and says why.
- **Daemon:** pause and resume (also timed, `until_ms`); upload, cache, provider and credential health and an upload attempt limit with the next try in
  `daemon.status`; `history.list` / `history.subscribe` over the transfer history; per-minute request roll-ups; a machine-readable `last_error_code`;
  write-handle ids issued by the daemon; a fail-fast on credentials that need an interactive sign-in.
- **CLI:** the account lifecycle (`profile list --json`, `profile set`, `profile default`, non-interactive `profile add`, `profile remove` that refuses a running
  or busy profile, `auth begin|complete|login`, `logout --json`), `scope show|set|clear` for the standing sync scope, `pending list|drop` to recover stranded
  upload rows, a periodic daemon health line.
- **State:** `state.db` in WAL mode with `synchronous=FULL`, a faster writer path, an in-memory row count, the staged scan in a file of its own, and merges
  in bounded chunks: far shorter holds of the state monitor on large drives.
- **Internxt:** resumable folder walks, folder paths resolved from the rows the listing saw, shard hash verification (RIPEMD-160 of SHA-256), permanent
  download failures told apart.
- **Duplicates:** remote items with the same name are kept under decorated names and listed in status.

## Fixed (selected)

Data safety and correctness:

- A remote rename onto an existing local file keeps that file as a conflict copy; a conflict whose download fails leaves no empty stub; keep-both copies never
  overwrite an earlier copy; a new file is never taken for a sparse stub by its content.
- A hydrated file whose new cloud content has not been downloaded yet is no longer treated as in sync; a remote rename that comes with an edit fetches the
  edit.
- `StateDatabase.batch` rolls back on an `Error` instead of committing half; the delta merge finds a row by its remote id first, so swapped and chained
  renames keep each row's baseline; an item that changes kind (file/folder) starts a row of its own.
- A mount no longer writes back a row for a cold read that finished after the file was deleted or renamed; an unsynced edit is remembered with the version it
  started from and replayed against it.
- `conflicts restore` writes under the sync root; a move in localfs never overwrites, a copy goes through a staging file; a file the hash compare cannot read
  no longer aborts the local scan.
- QuickXorHash follows Microsoft's algorithm (the earlier one produced other values and overflowed at about 186 MiB).

Security:

- Sign-out revokes the token where the provider has a revoke call (Dropbox) and no longer claims `revoked: true` otherwise; the vault is replaced atomically
  through an owner-only temp file; pre-authenticated URLs in exception text no longer reach logs, the audit log or IPC; the OAuth loopback wait, IPC UTF-8
  lines, the pid file, owner-only temp copies and pending sign-in files were hardened; pending device-flow credentials are cleaned on logout.

Providers:

- Internxt: a failing proactive token refresh keeps a still valid token in use; a file is found by its full name only (no base-name fallback); a download is no
  longer cut at 600 s in total; resumed scans keep the modification time; hex decoding accepts ASCII digits only.
- OneDrive keeps the stored refresh token when a refresh omits it, follows `sharedWithMe` paging; S3 treats a 403 for one object as that, not as a failed sign-in;
  S3 and Dropbox uploads are no longer cut by the 60 s socket timeout.

## Since the first draft (2026-10-24 to 2026-11-04)

About 205 merged pull requests: 132 fixes, 15 features, 3 performance changes, the rest tests, refactors, docs and dependency bumps. Selected, by what a user notices.

New:

- **Mount and client contract:** `hydration.list` names the bytes of each file (`content_id`), so a client tells a rename from new bytes; it reads a folder live while the
  first scan has not brought it in; a running download reports `downloading` events and a cancel or a disconnect stops it. `daemon.status` gains a `requests`
  object (what the engine's own requests are doing; Internxt today), a quota snapshot and every daemon log line names its profile and build.
- **Internxt:** the cursor gather streams through the staging instead of holding the account; a strict-names mode refuses (and reads backwards: quarantines and
  counts) names the official clients reject; the Favorites view lists favorited folders as read-only aliases; the account's backup devices are known, and shown in a
  second read-only root behind a switch that stays off.
- **CLI:** `dedupe` lists duplicate remote items and what a keep rule would do, `dedupe --apply` moves the twins a keep rule does not keep to the provider's trash;
  `auth login` reads the e-mail and the two-factor code from stdin; profile keys for the backups folder (still off unless set).

Data safety (deletes and edits meeting each other):

- A remote delete keeps a local edit made after the scan as a conflict copy; a folder delete defers to an edit a child delete kept aside; a locally deleted
  folder's remote delete waits for the child fetches planned below it; a remote rename inside a locally deleted folder is not deleted with the folder; a
  streaming drain keeps a delete of the item it just downloaded; a failed remote delete or move is retried after the cursor moves.
- A replace-rename stopped half way is finished or undone at the next start and deletes the old destination only after the source's move; short downloads are
  rejected and unchanged quarantines retained; a mount keeps a cache copy that was edited while the daemon was stopped; the retire move of `migrate-convert`
  stages and hash-verifies a cross-volume copy before the source is given up; a junction is a leaf for deletes, copies and scans; a backslash in a POSIX name stays.
- Uploads: a 402 plan limit fails once with a reason instead of 40 retries; a refused write is adopted or both copies are kept; the upload session stores are one
  atomic file layer.

Providers:

- OneDrive: a lost answer to the final upload chunk is resolved as the committed upload, not read as an expired session; the hash is QuickXor only; an item
  flagged as malware is refused and a OneNote notebook is left out of the listings; one delta item that does not decode is skipped, not the whole page; every throttle
  wait obeys one cap and one floor; a drive answer without a quota is an unknown quota; the refresh token and the pending flow are protected at rest.
- Internxt: the delta cursor comes from the server's time, so a client clock ahead of the server loses no remote change; a poll verifies its changed rows against the
  folder contents; a trash the index lags is reaped at once; a Retry-After of zero waits the one-second floor; a transient 5xx on a write is retried only where its repeat is safe (a repeated trash that answers 400 after a 5xx counts as
  committed); shard failures carry the host's Retry-After.
- S3 and Dropbox: the one-second throttle floor, hashes, times and keys that tell the truth, download timeouts sized from the declared size, one shared retry driver.

Security and build:

- Secrets are masked in `toString` (providers, bridge mirror, pending sign-in flow); error text sent to IPC clients is redacted; Dropbox tokens are protected at rest;
  the bearer token goes only to the Graph origin; the engine JVM trusts the Windows certificate store, so an antivirus that scans HTTPS no longer breaks it.
- The release pipeline runs with least privilege and verifies its artefacts; publisher keys are pinned in the verification metadata; CI boots the jlink runtime image
  and the Windows launcher resolves its runtime (and fails on an `UNIDRIVE_JAVA` that points nowhere); the IPC request cap counts each request line, not the raw read.

Performance: reads of `state.db` run on read-only connections beside the writer, two unused indexes are gone, subtree queries seek path ranges and `history.list`
with a result filter seeks its rows.

## Behaviour changes to know

- Several CLI failure paths now exit non-zero (`trash restore`, `versions restore`, `free`, `get` after skipped downloads, `sync --watch` stopped by an
  authentication error), and `free` refuses a file that was never uploaded.
- Configuration values the schema refuses are refused by key name with exit 78 (`poll_interval` below 5, an unknown `sync_direction`, a negative
  `hydration_cache_max_bytes`) instead of failing later or being read leniently.
- `trash purge` and `versions purge` use the profile's configured retention (`trash_retention_days`, `version_retention_days`) instead of fixed 30 and 90 days,
  and print the value and its source.
- `profile add` for a backup profile writes a mirror profile the parser reads, with its upload policy in a section of its own.
- Windows device names (`CON`, `NUL`, `COM0` ...) are refused by one shared rule for engine, profile and folder names.
- `state.db` is stamped schema 3 at the first start of this build; an older engine (all of them know schema 2) then refuses to open that file instead of
  resetting columns it does not know. Keep a copy of `state.db` before the first start if you may go back.
- `max_bandwidth_kbps` bounds the combined rate of all running transfers (it used to bound each transfer on its own) and no longer holds a transfer slot while it waits.
- `sync --reset` and `refresh --reset` ask first and copy `state.db` aside; `relocate` refuses to run until its data-loss defects are fixed.
- `exclude_patterns` are checked by the matcher's own compile step and match non-BMP characters and `a/**/b`; `status` counts them in the out-of-scope line.
- A 402 plan limit fails an upload once with its reason instead of retrying it 40 times.

## Compatibility

The IPC protocol version stays 2; the additions to `daemon.status`, `history.*` and the corpus are additive. Under the 0.x rule of the distribution design
(0.MINOR for a breaking CLI or IPC change) the exit-code and validation changes above are the ones to weigh; they are the only places an existing script could
notice a difference. The schema 3 stamp of `state.db` is the one change that cannot be undone by installing an older engine (see above); the `daemon.status`
`requests` object and the `content_id` of `hydration.list` are additive and absent for a provider that cannot report them.
